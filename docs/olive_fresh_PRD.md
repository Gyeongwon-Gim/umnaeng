# PRD: 생성형 AI 기반 냉장고 관리 앱 (가칭: 냉장고 지킴이)

- 문서 버전: v0.1 (초안)
- 작성일: 2026-07-24
- 상태: Draft — 팀 리뷰 대기

---

## 1. 개요 (Overview)

냉장고 속 식재료와 반찬은 "넣는 순간 잊히는" 문제를 갖는다. 무엇이 있는지, 언제 넣었는지, 언제까지 먹어야 하는지를 기억에 의존하기 때문에 음식물 폐기와 중복 구매가 반복된다.

본 제품은 **사진 한 장으로 등록이 끝나는** 냉장고 관리 앱이다. 생성형 AI(Vision LLM)가 사진에서 음식을 자동 인식하고 보관기한을 자동 산정하며, 사용자는 기한 임박 순으로 정렬된 리스트에서 스와이프 제스처만으로 재고를 관리한다.

핵심 가치 제안: **"등록 3초, 관리 스와이프 1번."**

## 2. 문제 정의 (Problem Statement)

1. 수동 입력의 마찰: 기존 냉장고 관리 앱은 품목명·수량·유통기한을 직접 입력해야 해서 며칠 쓰다 포기하게 된다.
2. 기한 인지 실패: 냉장고를 열어보기 전까지는 무엇이 임박했는지 알 수 없고, 열어봐도 날짜를 일일이 확인해야 한다.
3. 냉동실 착시: "냉동하면 안 상한다"는 인식 때문에 냉동실이 장기 방치 창고가 된다.

## 3. 목표 및 성공 지표 (Goals & Metrics)

### 목표
- G1. 등록 마찰 최소화: 사진 업로드 → 인식 → 저장까지 사용자 조작 3회 이내
- G2. 폐기율 감소: 기한 만료로 삭제되는 항목 비율 감소
- G3. 습관화: 주 2회 이상 앱을 여는 리텐션 확보

### 성공 지표 (KPI)
| 지표 | 정의 | 목표 (출시 3개월) |
|---|---|---|
| 등록 완료율 | 사진 업로드 시작 대비 저장 완료 비율 | ≥ 85% |
| AI 인식 수정률 | 사용자가 AI 인식 결과를 수정한 비율 | ≤ 30% |
| 기한 내 소진율 | 만료 전에 소진 처리된 항목 비율 (소진 시점 vs 기한 비교로 자동 산출) | ≥ 60% |
| 알림 → 앱 진입 전환율 | 임박 알림 탭 비율 | ≥ 25% |
| W2 리텐션 | 설치 2주 후 잔존율 | ≥ 30% |

## 4. 타깃 사용자 (Target Users)

- 주 페르소나: 1~2인 가구 직장인. 장은 주 1회, 배달·반찬가게 이용 잦음. 냉장고 파악이 안 돼 같은 재료를 또 산다.
- 부 페르소나: 반찬을 대량으로 만들어 보관하는 가족 단위 사용자. 만든 날짜 기억이 어려움.

## 5. 기능 요구사항 (Functional Requirements)

### FR-1. 사진 기반 자동 등록
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1.1 | 사용자는 카메라 촬영 또는 갤러리 업로드로 사진을 등록할 수 있다. | P0 |
| FR-1.2 | 생성형 AI(Vision 모델)가 사진 속 음식을 인식하여 품목명·분류(식재료/반찬/완제품)·수량(추정)을 반환한다. | P0 |
| FR-1.3 | 한 장의 사진에서 복수 품목 인식을 지원한다. (예: 반찬통 3개 → 3개 항목 제안) | P1 |
| FR-1.4 | 인식 결과는 저장 전 확인 화면에서 수정 가능하다. (품목명 변경, 항목 삭제/추가) | P0 |
| FR-1.5 | 인식 실패 또는 신뢰도 낮음(임계값 미만) 시, 후보 리스트 + 직접 입력 폴백을 제공한다. | P0 |
| FR-1.6 | 포장 제품의 유통기한 표기가 사진에 보이면 OCR로 읽어 보관기한에 우선 적용한다. | P1 |

### FR-2. 보관기간 자동 설정
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-2.1 | AI가 품목·조리 상태(생물/조리됨)·보관 위치(냉장/냉동)를 기반으로 권장 보관기한을 자동 산정한다. | P0 |
| FR-2.2 | 기한 산정 근거를 짧게 표시한다. (예: "조리된 나물류는 냉장 3~4일 권장") | P1 |
| FR-2.3 | 사용자는 자동 산정된 기한을 수동으로 수정할 수 있다. | P0 |
| FR-2.4 | 등록일(입고일)은 기본값 오늘이며 수정 가능하다. (예: 어제 만든 반찬) | P1 |

기한 산정 정책: 식품안전 가이드라인(식약처 등) 기반의 카테고리별 기준표를 프롬프트/룰로 내장하고, AI 응답은 이 기준표 범위로 클램핑한다. AI 환각으로 비상식적 기한(예: 생선회 냉장 14일)이 나오는 것을 방지.

### FR-3. 리스트 뷰 — 우선순위 큐 정렬
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-3.1 | 보관 중인 전 품목을 리스트 뷰로 표시한다. 각 행: 썸네일, 품목명, 보관 위치, 남은 일수(D-n). | P0 |
| FR-3.2 | 기본 정렬은 남은 기한 오름차순(임박 항목이 최상단). 우선순위 큐와 동일하게 만료 임박 항목이 항상 위로 올라온다. | P0 |
| FR-3.3 | 냉장/냉동 탭(또는 필터)을 제공한다. 전체 탭에서는 위치 무관 임박 순 통합 정렬. | P1 |
| FR-3.4 | 만료 경과 항목(D+n)은 최상단에 별도 구분(만료 섹션)으로 표시한다. | P1 |

### FR-4. 임박도 시각화 (색상)
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-4.1 | 남은 기한에 따라 각 항목에 상태 색상을 적용한다. | P0 |
| FR-4.2 | 색상만으로 구분하지 않고 D-n 텍스트를 병기한다. (색각 이상 접근성) | P0 |

색상 정책 (기본값, 추후 A/B 조정):
- 🟢 여유 (Green): 남은 기한이 전체 보관기간의 50% 초과
- 🟡 주의 (Yellow): 남은 기한 50% 이하 또는 D-3 이내
- 🔴 임박 (Red): D-1 이하
- ⚫ 만료 (Gray/Red 강조): D+0 경과

절대 일수(D-3)와 비율(50%) 중 더 임박한 기준을 적용한다. 보관기간이 짧은 반찬(3일)과 긴 소스류(3개월)를 동일한 절대 기준으로 다루면 왜곡되기 때문.

### FR-5. 임박 알림 (Push Notification)
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-5.1 | 항목이 🔴 임박 상태 진입 시(D-1) 푸시 알림을 발송한다. | P0 |
| FR-5.2 | 복수 항목 임박 시 개별 발송이 아닌 1건으로 묶어 발송한다. (예: "오늘 안에 먹어야 할 항목이 3개 있어요") | P0 |
| FR-5.3 | 알림 발송 시각은 사용자 설정 가능(기본 오전 9시). | P1 |
| FR-5.4 | 알림 탭 시 리스트 뷰(임박 항목 상단)로 진입한다. | P0 |
| FR-5.5 | 🟡 주의 단계 사전 알림은 옵션(기본 off). | P2 |

### FR-6. 좌측 스와이프 — 소진/삭제
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-6.1 | 리스트 항목을 좌측으로 스와이프하면 해당 항목을 소진 처리(리스트에서 제거)한다. | P0 |
| FR-6.2 | 오조작 방지를 위해 삭제 직후 실행 취소(Undo) 스낵바를 5초간 노출한다. | P0 |
| FR-6.3 | 소진 이력(품목·소진 시점)은 통계 화면에서 조회 가능하다. 만료 전/후 소진 여부는 시점 비교로 자동 산출한다. | P2 |

### FR-7. 우측 스와이프 — 냉동실 이동
| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-7.1 | 냉장 항목을 우측으로 스와이프하면 냉동실로 이동한다. | P0 |
| FR-7.2 | 이동 시 냉동 기준 보관기한으로 재계산한다. (품목별 냉동 권장 기한 적용) | P0 |
| FR-7.3 | 이동 시 안내 메시지를 표시한다: "냉동해도 품질은 계속 떨어져요. 늦어도 N주 안에 드시는 걸 권장해요." — 냉동 = 무기한이라는 인식을 교정하는 카피를 사용한다. | P0 |
| FR-7.4 | 냉동 항목도 동일한 임박도 색상·알림 체계를 따른다. | P0 |
| FR-7.5 | 이미 냉동 상태인 항목의 우측 스와이프 동작은 비활성 또는 "냉장 해동으로 이동"(정책 결정 필요, §9). | P1 |

## 6. 비기능 요구사항 (Non-Functional Requirements)

| ID | 항목 | 기준 |
|---|---|---|
| NFR-1 | AI 인식 응답 시간 | 업로드 → 결과 표시 p90 ≤ 5초. 처리 중 스켈레톤/진행 UI 필수 |
| NFR-2 | 이미지 처리 | 업로드 전 클라이언트 리사이즈(장변 1280px)로 비용·지연 절감 |
| NFR-3 | 오프라인 | 리스트 조회·스와이프는 로컬 캐시로 오프라인 동작, 등록(AI 호출)은 온라인 필수 |
| NFR-4 | 개인정보 | 사진은 인식 처리 후 원본 미보관(썸네일만 보관) 또는 보관 시 명시 동의. AI 학습 미사용 고지 |
| NFR-5 | 비용 | 인식 1회당 LLM API 비용 상한 설정, 월별 사용자당 호출 쿼터 검토 |
| NFR-6 | 접근성 | 색상 + 텍스트 병기, 스와이프 대체 수단(길게 눌러 메뉴) 제공 |

## 7. 사용자 흐름 (Key User Flows)

### 등록 흐름
1. [+] 버튼 → 카메라/갤러리 선택
2. 사진 업로드 → AI 인식 (로딩 UI)
3. 확인 화면: 인식된 품목 카드 목록 (품목명 / 보관위치 / 자동 산정 기한 + 근거)
4. 수정 필요 시 인라인 편집 → [저장]
5. 리스트 뷰로 복귀, 신규 항목이 정렬 위치에 삽입됨

### 관리 흐름
1. 아침 9시 알림: "오늘 안에 먹어야 할 항목이 2개 있어요"
2. 탭 → 리스트 뷰 진입, 🔴 항목이 최상단
3. 먹은 항목 → 좌측 스와이프 → 소진 (Undo 5초)
4. 못 먹을 항목 → 우측 스와이프 → 냉동 이동 + 권장 소진 기한 안내 메시지

## 8. 범위 제외 (Out of Scope — v1)

- 레시피 추천 (임박 재료 기반) → v2 후보
- 바코드 스캔 등록 → v2 후보
- 가족 간 냉장고 공유(멀티 유저 동기화) → v2 후보
- 냉장고 IoT 연동
- 장보기 리스트 자동 생성

## 9. 결정 필요 사항 (Open Questions)

1. 냉동 → 냉장(해동) 이동 UX: 우측 스와이프의 역방향을 어떻게 처리할지. (냉동 탭에서는 우측 스와이프 = 해동 이동?)
2. 만료 항목 자동 처리: D+7 경과 항목을 자동 아카이브할지, 사용자가 직접 지울 때까지 둘지.
3. Vision 모델 선정: 정확도 vs 비용 vs 지연. 자체 프롬프트 기반 범용 LLM(예: Claude Vision) vs 음식 특화 분류 모델 + LLM 하이브리드.
4. 수량 관리: "계란 10개 중 3개 사용" 같은 부분 소진을 v1에서 지원할지, 항목 단위 소진만 할지.
5. 동일 품목 중복 등록 처리: 같은 반찬을 두 번 찍으면 병합 제안할지.
